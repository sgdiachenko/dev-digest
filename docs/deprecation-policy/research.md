# Deprecation policy: як дати consumers безпечний шлях міграції

Статус: дослідницька база активного
[`deprecation-policy`](../../.claude/skills/deprecation-policy/SKILL.md), **не
затверджена політика релізів**. Перевірено 2026-09-18. Повний
[реєстр джерел](sources.md) зведено також у README скіла.

Головне питання: якщо контракт видаляється, перейменовується або замінюється,
чи отримали його consumers повідомлення, працездатну альтернативу або шлях
відмови, інструкції та реальний час на перехід?

Далі S1–S9 посилаються на реєстр джерел. Позначення **локальна пропозиція**
означає рекомендацію для майбутнього скіла, а не вимогу зовнішнього стандарту.

## 1. Коли застосовувати

**Локальна пропозиція.** Застосовувати під час review diff або явно замовленого
аудиту життєвого циклу backend-контрактів:

- Видалення, перейменування, заміна HTTP endpoint, поля DTO, параметра,
  заголовка, публічної функції, типу або підтримуваного import path.
- Зміна спостережуваної семантики: одиниць виміру, defaults, статусів,
  помилок, гарантій завершення, авторизації — якщо старі consumers мають
  мігрувати. Сумісність охоплює source, wire та semantics. [S6](sources.md)
- Початкове оголошення deprecation, зміна його строків або заміни,
  видалення alias, wrapper, старої версії чи іншого compatibility-механізму.
- Підготовка major-релізу з несумісними API-змінами. Сам факт major-бампу
  без зміни/припинення контракту не є достатнім тригером.

Не застосовувати до суто внутрішнього перейменування, невикористаного
приватного helper або DB-рефакторингу без впливу на підтримуваний контракт.
`export` потрібен і для внутрішніх модулів: встановлювати публічність за
документацією, підтримуваними entrypoints, залежностями й гарантіями, а не
за одним ключовим словом. Відсутність callers у repo не доводить відсутності
зовнішніх consumers. Якщо межа невідома — зафіксувати невизначеність.

### Відношення до breaking-change та версій

[breaking-change](../../.claude/skills/breaking-change/SKILL.md) відповідає,
чи перестане працювати старий consumer. Цей майбутній скіл оцінює підготовку
переходу. **Локальна пропозиція:** спільний finding має містити і конкретний
break, і відсутній міграційний захід; не створювати два findings про одне
видалення. Навіть добре підготовлене видалення лишається breaking change.

Для стабільного SemVer API несумісність вимагає major; deprecation належить
до minor-релізу (може входити й до ширшого major). FAQ радить щонайменше один
minor із deprecation перед видаленням у major. Це не мінімальна кількість
днів. У `0.x` SemVer не обіцяє стабільності. [S1](sources.md)

У dev-digest `server` і `reviewer-core` мають `0.0.0` та `private: true`;
їхній package version не є автоматично версією HTTP API. **Локальна
пропозиція:** перевіряти фактичні обіцянки consumers незалежно від `0.x`;
не вимагати механічного npm major-бампу для кожної HTTP-зміни й не дозволяти
тихе видалення лише через `private`. Обидві копії shared contracts і новий UI
в одному PR не захищають уже розгорнуті старі клієнти.

## 2. Як перевіряти: докази та п'ять критеріїв

**Локальна пропозиція — workflow для майбутнього скіла.**

1. Встановити baseline: надана база або merge-base цільової гілки; для
   локального review включити staged/unstaged/untracked зміни. Без старої
   версії контракту не оголошувати сумісність перевіреною.
2. Знайти публічну поверхню та consumers. Для HTTP простежити повний method
   + path, schema, serializer і поведінку; для exports — підтримуваний шлях
   імпорту, сигнатуру, типи та runtime-семантику.
3. Встановити стадію: оголошення, період міграції чи фактичне видалення.
   Перевірити документацію, попередні релізи, tags, опубліковані артефакти,
   runtime-маркери, тести старого consumer. Коміт у нерелізнутій гілці ще
   не доводить, що consumers отримали попередження.
4. Для кожного критерію нижче дати результат: підтверджено, відсутнє,
   невідомо або обґрунтовано не застосовується. Прив'язати до доказу.
5. Перевірити реальну доступність старого API й заміни; документація або
   успішна компіляція нового клієнта не є доказом compatibility window.

| Критерій | Достатній доказ | Типова помилка |
|---|---|---|
| Deprecation marker | Позначення доступне відповідним consumers і точно називає застарілий контракт: docs/release notes, TSDoc, OpenAPI або HTTP-повідомлення. | Коментар `TODO: remove` у приватному service; маркер додано тільки в PR видалення. |
| Replacement | Альтернатива вже доступна для відповідного середовища; описано функціональні відмінності та обмеження. Без альтернативи — причина й шлях припинення використання. | Посилання на ще не випущений endpoint або припущення, що новий API має ідентичні можливості. |
| Migration path | Кроки та приклади до/після: imports/requests/responses, потрібна версія, зміни даних і порядок розгортання, якщо релевантно. | «Оновіть клієнт» без mapping полів і зміни семантики. |
| Removal timeline | Конкретна дата/версія, умови видалення або явне «видалення не заплановано». | `soon`, суперечливі дати, або дата вимкнення раніше deprecation. |
| Compatibility window | Обіцяний строк із визначеним початком; старий контракт і доступна заміна співіснують потрібний час. Для removal є історія оголошення та докази завершення вікна. | Позначити й видалити в одному релізі; вважати alias сумісним, хоча він змінює response. |

Цей чекліст — локальна пропозиція. Механізми позначення описують S2–S5;
пояснення альтернативи або її відсутності підтримує S8. Вимірювані процеси
переходу і стабільність заміни ілюструють S7 та S9. [Джерела](sources.md)

### Маркери залежать від consumers

- Для TypeScript: `@deprecated` із рекомендованою альтернативою на
  публічному символі; перевірити, що consumers бачать цей коментар. [S5](sources.md)
- Для OpenAPI: `deprecated: true` на відповідній операції/параметрі;
  пояснення переходу в документації. Це metadata, а не runtime-shim. [S4](sources.md)
- Для HTTP: `Deprecation` сигналізує дату deprecation; `Link` із
  `rel="deprecation"` може вести до інструкції. Scope повідомлення має
  відповідати ресурсу або бути явно задокументованим. [S2](sources.md)

**Локальна пропозиція:** не вимагати одночасно всі маркери. Сам TSDoc у
server-коді не повідомляє незалежного HTTP consumer. Не оголошувати весь
endpoint застарілим без пояснення, коли deprecated лише одне поле.

## 3. Життєвий цикл і рішення про видалення

**Локальна пропозиція:** описувати кожну міграцію таким компактним записом:

```text
Контракт і consumers:
Причина deprecation:
Заміна / причина її відсутності:
Оголошено: дата + опублікований реліз/канал
Deprecated з: дата/версія
Міграція: інструкція + приклади
Видалення: не раніше дати/версії + умови, або не заплановано
Підтримка: що працює до видалення, як визначається строк
Докази: старий consumer, релізи, результати перевірок
Відповідальний за рішення:
```

На стадії оголошення перевіряти, що старий контракт працює, а перехід
здійсненний. При видаленні — що обіцяне вікно минуло, consumers отримали
інструкції й немає суперечності з чинними гарантіями. Якщо policy поєднує
дату та кількість релізів, виконати обидві умови. Не вигадувати 30/90/180 днів:
брати строк із підтримуваної політики; його відсутність — evidence gap.

Явне «видалення не заплановано» допустиме для deprecation, але не дозволяє
потім видалити API без нового повідомлення та визначеного переходу.
Якщо заміна доступна пізніше оголошення, перевірити, скільки часу consumers
насправді мали для міграції; не зараховувати недоступну заміну як готовий шлях.

**Локальна пропозиція для винятків:** термінове усунення небезпечного API
може скоротити звичайне вікно. Потрібні документовані причина, масштаб,
відповідальний за рішення, спосіб сповіщення й mitigation для consumers.
Не вимагати залишати небезпечний API активним заради формального чекліста;
позначити зміну як breaking із винятком, а не як сумісну. AIP-181 розглядає
emergency changes, але конкретна процедура тут є локальною пропозицією. [S7](sources.md)

## 4. Погані та хороші практики

Нижче — **ілюстративні локальні рекомендації**, не опис реальних endpoints
або обіцянка конкретних строків dev-digest.

| Погано | Добре |
|---|---|
| Видалити `GET /repos/:id/reviews`, бо власний UI уже використовує новий URL. | Зберегти старий handler/адаптер зі старим status, body та semantics на оголошений період; дати mapping нового URL й перевірити старий client fixture. |
| Замінити request `repo_id` на `repository_id`, мовчки відкидаючи старе поле. | Підтримувати старий payload, нормалізувати обидві назви всередині; задокументувати, що робити, якщо передано обидві. Правило конфлікту перевірити проти раніше валідних запитів. |
| Видалити response-поле `findings_summary`, бо нове має кращу назву. | Зберегти старе поле та його значення на перехідний період; нове додавати лише з урахуванням декодерів consumers або в окремій версії. |
| Додати `@deprecated` і видалити функцію в тому самому релізі. | Спочатку випустити deprecated wrapper зі старою сигнатурою й поведінкою, доступну заміну та migration guide; видалити після виконання оголошених умов. |
| Написати «буде видалено скоро». | Вказати дату/версію та умови або явно «видалення не заплановано». |
| Зробити major-бамп і вважати міграцію завершеною. | Перевірити оголошення, історію підтримки, доступність заміни й migration guide окремо від номера версії. |
| Видалити API без заміни й вигадати формальний replacement. | Пояснити припинення можливості та дати порядок відмови від неї, включно з експортом даних, якщо релевантно. |
| Зберегти redirect і назвати це compatibility layer. | Перевірити метод, body, auth, статуси й підтримку redirects старим клієнтом; за потреби залишити серверний адаптер. |

### Приклад програмного API

Припустімо, нова функція має ту саму семантику та повертає той самий
`Promise<Review[]>`. Wrapper зберігає попередній import path, а реліз 1.8.0
опублікував попередження; дата видалення визначається реальною політикою.

```ts
/**
 * @deprecated Use listReviews({ repoId }) instead.
 * Deprecated since 1.8.0. Removal is not scheduled.
 * Migration: replace getReviews(repoId) with listReviews({ repoId }).
 */
export function getReviews(repoId: string): Promise<Review[]> {
  return listReviews({ repoId });
}
```

`@deprecated` відповідає TSDoc; версія, timeline й крок міграції — додатковий
локальний приклад. Wrapper не доводить сумісності, якщо нова функція змінює
фільтрацію, порядок або помилки. [S5](sources.md)

### Приклад HTTP-повідомлення

Ілюстративні дати: deprecation 2026-01-01 00:00:00 UTC, очікуване вимкнення
2027-01-01 00:00:00 UTC. Це не запропонований річний SLA.

```http
Deprecation: @1767225600
Sunset: Fri, 01 Jan 2027 00:00:00 GMT
Link: <https://api.example.com/migrations/reviews>; rel="deprecation"; type="text/html"
```

У `Deprecation` використовується structured date, не `true` і не HTTP-date;
у `Sunset` — HTTP-date. Sunset не передує Deprecation. Заголовок Deprecation
сам по собі не змінює поведінку ресурсу. [S2](sources.md)

Sunset передає очікування щодо доступності URI, не гарантує конкретний
`404`/`410` після дати й не є доказом обіцяної підтримки. Якщо вимкнення не
заплановане, не вигадувати Sunset. Підтримку забезпечують реалізація та
політика; migration guide має містити фактичні кроки. [S3](sources.md)

## 5. Сценарії перевірки скіла

Це **локально запропоновані поведінкові сценарії**, а не вже виконані тести
скіла. Вони потрібні для подальшого behavior-тестування та уточнення правил.

| Сценарій | Очікувана оцінка |
|---|---|
| Перейменовано внутрішній helper, контракт не змінився. | Не застосовується; не вимагати deprecation. |
| Deprecated wrapper випущено, заміна працює, є інструкція, видалення не заплановане. | Оголошення підготовлене; не вимагати вигаданої дати. |
| Старий endpoint видалено без повідомлення. | Підтверджений недолік процесу та breaking change, об'єднані в один finding. |
| Маркер є, але немає доступу до історії релізів. | Не перевірено, чи consumers мали вікно; не стверджувати ані проходження, ані доведену відсутність повідомлення. |
| Вікно минуло, усі охоплені consumers мігрували, release policy дозволяє removal. | Процес видалення підтверджений; несумісність старого контракту все одно явно зазначена. |
| Мігрував лише поточний UI, інших consumers не досліджено. | Недостатньо доказів повної міграції. |
| Дата минула, але обіцяна кількість релізів ще не вийшла. | Видалення передчасне, якщо policy вимагає виконати обидві умови. |
| Replacement відсутній, але причина й план припинення використання документовані. | Не створювати finding лише через відсутність заміни; перевірити решту критеріїв. |
| Документований emergency security removal. | Позначити виняток і breaking impact; не вимагати відновлення небезпечного API. |
| Alias залишився, але змінив результати або помилки. | Compatibility window не доведене самим alias; перевірити конкретного старого consumer. |

**Локальна пропозиція для звіту:** один підсумок — «шлях переходу
підтверджено», «виявлено недоліки», «не перевірено» або «не застосовується».
Для кожного finding: контракт, місце зміни, стадія, порушений критерій,
доказ, consumer impact і конкретне виправлення. Підтверджені недоліки
відокремлювати від браку даних. Не вводити автоматичний CRITICAL gate;
у PR self-review дотримуватися його severity-правил.

Для реалізації міграції релевантні тести старих request/response fixtures
проти нового server, старих imports і викликів проти wrapper, а також
перевірка marker metadata та послідовності дат. Не підміняти їх тестами
тільки нового клієнта. Створення скіла не змінює runtime продукту, тому
application-тести для цього етапу не потрібні.
