# Дослідження для semver-discipline

Дата перевірки джерел: **2026-09-18**. Статус: дослідницька основа для
майбутнього скіла та його README; це не затверджена release-політика.

## Мета та межі

`semver-discipline` має відповідати: **чи відповідає запланована версія
масштабу зміни публічного контракту?** Він використовує докази несумісності,
а не дублює повний пошук дефектів у `breaking-change` та `response-schema`.

Матеріал розрізняє:

- **Нормативне правило** — вимога SemVer для продукту, який його дотримується.
- **Рекомендацію джерела** — практика конкретної екосистеми чи інструмента.
- **Проєктне рішення для майбутнього скіла** — запропонована методика review,
  а не нове зобов'язання для всіх пакетів репозиторію.

## Локальний контекст

Перевірені [server/package.json](../server/package.json),
[client/package.json](../client/package.json) та
[reviewer-core/package.json](../reviewer-core/package.json) містять
`version: "0.0.0"` і `private: true`. Пошук у README, `docs/`, `server/docs/`
та `.github/` не виявив явної SemVer/release-політики. Це обмежений результат
інспекції, а не доказ відсутності зовнішнього процесу релізів.

За [AGENTS.md](../AGENTS.md), пакети самостійні, а `@devdigest/shared` —
дзеркальні контракти, не опублікований пакет. Не слід вигадувати для кожного
backend-модуля чи каталогу контрактів окрему версію. `private: true` саме по
собі не визначає гарантій HTTP API.

**Узгоджене рішення:** за відсутності політики давати умовну рекомендацію
«якщо цей пакет/API дотримується SemVer…» та позначати невизначеність.
Не оголошувати доведеним порушенням відсутність major-бампу в цьому проєкті.

## Нормативна основа

За [S1](https://semver.org/spec/v2.0.0.html):

| Умова | Правило |
|---|---|
| Використання SemVer | Потрібен визначений public API. |
| Стабільна версія `X > 0`, несумісна зміна public API | Major; minor і patch скидаються в нуль. |
| Сумісна публічна функціональність або оголошення deprecation | Minor; patch скидається в нуль. |
| Лише сумісне виправлення помилки | Patch. |
| `0.y.z` | Початкова розробка; стандарт дозволяє зміни без стабільних гарантій. |
| Prerelease | Нестабільна версія, нижча за відповідний звичайний реліз. |
| Build metadata після `+` | Не впливає на пріоритет версій. |
| Уже опублікована версія | Її вміст не можна переписувати; потрібен новий реліз. |

FAQ S1 рекомендує задокументувати deprecation і випустити його перед
видаленням. Відрізняти цю рекомендацію від нормативної вимоги minor для
самого оголошення deprecation. Оновлення залежності оцінюється за власним
public API, а не лише за major-номером залежності.

## Коли застосовувати

Наступні тригери — **проєктна методика**, обґрунтована S1–S6:

- Є підтверджена зміна публічного контракту: видалення, перейменування,
  зміна типу, допустимих запитів або гарантованої поведінки.
- Додається сумісна публічна можливість чи оголошується deprecation.
- PR змінює версію, release intent, changelog або налаштування визначення bump.
- Готується реліз із кількох PR або перевіряється відповідність релізу змінам.
- Користувач прямо просить перевірити дисципліну версійності.

Внутрішній рефакторинг без впливу на public API не є підставою для major.
Docs-only зміни не потребують автоматичного bump, але оголошення deprecation
у документації не можна помилково класифікувати як звичайну правку тексту.

## Процедура перевірки

Це **проєктне рішення для майбутнього скіла**; джерела пояснюють принципи,
але не диктують точного алгоритму агентного review.

1. **Встановити одиницю версіонування.** Знайти, що саме версіонується:
   пакет, сервіс або HTTP API. Прочитати політику, відповідні manifest,
   release config, changelog і теги. Не вважати `package.json`, `/v1` та
   `info.version` взаємозамінними. Джерела: S1, S3, S7.
2. **Зафіксувати дві бази порівняння.** Для внеску PR використати задану
   користувачем базу або merge-base цільової гілки; для рівня релізу —
   останній відповідний опублікований реліз цієї одиниці. Врахувати вже
   заплановані зміни та локальний diff у локальному review. Не підміняти
   release baseline довільним `HEAD~1`. Обґрунтування: S1, S6.
3. **Підтвердити масштаб.** Використати findings із
   [breaking-change](../.claude/skills/breaking-change/SKILL.md) та
   [response-schema](../.claude/skills/response-schema/SKILL.md), якщо вони
   доступні. Перевірити старий контракт і фактичний вплив на клієнта;
   невизначений finding не перетворювати на доведену вимогу major. За
   відсутності звітів зробити лише потрібну цільову перевірку. Джерело: S2.
4. **Визначити потрібний рівень.** Застосувати нормативну таблицю з урахуванням
   політики й stability channel. Для набору змін визначити максимальний
   необхідний bump окремо для кожної одиниці. Джерела: S1, S6.
5. **Перевірити заявлений реліз.** Якщо версія змінюється одразу — порівняти
   її з релізною базою. Якщо bump відкладений — перевірити прийнятий workflow
   та коректний release intent; у release PR перевірити підсумкову версію.
   Сам напис `BREAKING CHANGE` без відповідного процесу не доводить, що
   реліз буде правильним. Джерела: S4, S6.
6. **Сформувати висновок.** Вказати потрібний і заявлений рівні, докази,
   невідомі передумови та виправлення. Не вимагати додаткового major, якщо
   зміна вже входить у належний запланований major-реліз. Джерело: S6.

Бамп версії повідомляє про несумісність, але не виправляє її. Для HTTP API
окремо перевірити, як клієнт обирає версію та чи зберігається старий контракт;
саме перейменування серверного релізу не забезпечує міграції. S3 описує
співіснування версій як практику Google; конкретні строки не нав'язуються.

## Межові випадки та захист від хибних висновків

Ці рішення уточнюють застосування джерел до review, не створюють нових
універсальних вимог SemVer.

| Випадок | Як діяти | Основа |
|---|---|---|
| Немає політики або release baseline | Позначити невизначеність; дати умовну оцінку, не стверджувати порушення. | S1 + узгоджене рішення |
| Версія `0.x` | Шукати локальну політику; не оголошувати ані обов'язковий `1.0.0`, ані універсальне правило «breaking = minor». | S1 |
| `2.0.0-beta.1 → beta.2` | Перевірити гарантії каналу й цільовий стабільний реліз; не вимагати `3.0.0` лише через зміну beta-контракту. | S1 |
| Breaking проти стабільного `1.x`, ціль `1.5.0-beta.1` | Beta-мітка не доводить коректність майбутнього стабільного `1.5.0`; перевірити release intent для stable. | S1 + методика review |
| Змінилося лише `+build` | Не зараховувати як підвищення пріоритету релізу. | S1 |
| Dependency major без зміни власного контракту | Не переносити major автоматично; перевірити реальний вплив. | S1 FAQ |
| Публічна зміна називається `fix` | Класифікувати за контрактом; назва не спростовує breaking evidence. | S2, S4 |
| Response optional → required | Спочатку перевірити сумісність через response-schema; це не аналог нового required request-поля. Не вимагати major за самою назвою переходу. | S2 + напрямлена перевірка контракту |
| Реліз містить major і кілька patch-змін | Оцінювати агрегат для відповідного пакета, не додавати окремий major на кожен PR. | S6 |
| Заявлений bump більший за необхідний | Не називати це доведеною несумісністю; пояснити різницю й перевірити інші зміни релізу та політику. | Проєктне рішення |

| Підняти серверний package до `2.0.0`, залишивши старий URL із несумісною відповіддю, і заявити про збережену сумісність. | Розділити відповідність номера та міграцію клієнтів; якщо потрібна підтримка старих клієнтів, зберегти доступний старий контракт. | S2, S3 |

## Формат висновку майбутнього скіла

**Проєктне рішення:** один із результатів — **відповідає**, **не відповідає**,
**невизначено**; **не застосовується** для явно іншої схеми версіонування
або змін поза предметом перевірки. Відсутність політики — не автоматичний pass.

Кожен finding містить:

- Одиницю версіонування, політику, stability channel та release baseline.
- Зміну з `file:line`, старий контракт і доказ впливу на клієнта.
- Потрібний рівень, заявлену версію або release intent та джерело правила.
- Результат, впевненість, невідомі передумови та конкретне виправлення.

Приклад за доведеної політики: «Видалення гарантованого поля `name` порушує
контракт. Для API зі стабільною базою `1.4.2` запланований patch `1.4.3`
не відповідає масштабу зміни; потрібен major або збереження сумісності».

Приклад без політики: «Видалення `name` є підтвердженою несумісністю.
Якщо цей API дотримується стабільного SemVer, потрібен major замість
patch/minor. Політику й відповідну версію API не встановлено, тому
порушення версійності не підтверджене».

## Сценарії приймання майбутнього скіла

Це очікування для подальшої поведінкової перевірки, а не вже виконані тести.

| Вхід | Очікуваний результат |
|---|---|
| Стабільний SemVer, видалене required response-поле, patch | Не відповідає; доказ і major-рекомендація. |
| Та сама зміна вже включена в запланований major | Відповідає за номером; не заявляти про сумісність клієнтів. |
| Сумісна нова функція, minor | Відповідає. |
| Сумісне виправлення, patch | Відповідає. |
| Deprecation public API, patch | Не відповідає. |
| Належний major changeset, manifest ще не змінений, workflow підтверджений | Намір відповідає; фінальний реліз ще не перевірений. |
| `0.0.0`, політики немає | Невизначено; умовна рекомендація. |
| Несумісна зміна prerelease без відомих гарантій каналу | Невизначено; не переносити автоматично правила stable. |
| Лише build metadata замість потрібного bump | Не відповідає за підтвердженої SemVer-політики. |
| Лише оновлення версії специфікації OpenAPI | Не вважати доказом bump API. |
| Немає release baseline | Не вигадувати вихідну версію; вказати обмеження. |
| Внутрішній рефакторинг або response optional → required без порушення гарантій | Не вимагати major без іншого доказу несумісності. |
