> Статус: **звіт + пропозиції** (2026-09-23), до впровадження ще не погоджено.
> Джерело даних: фіча [Intent Layer](intent-layer.md), гілка `H03`, один сеанс Claude Code.
> Оновлення (2026-09-24, §5): другий вимір на фічі [Smart Diff](smart-diff.md) —

## 1. Звіт по витратах (Intent Layer)

Процес: researcher → planner → погодження → implementer → plan-verifier + architecture-reviewer →
8 виправлень → security review → doc-writer → `/pr-self-review` → логування промпта (у головній сесії).

| Етап | Агент / де | Токени | Викликів інструментів | Тривалість |
|---|---|---|---|---|
| Дослідження (репо + веб) | researcher | ~108k | 63 | ~5.8 хв |
| План | planner | ~179k | 42 | ~6.5 хв |
| Реалізація S1–S11 | implementer | ~446k | 224 | ~28 хв |
| 8 виправлень після рев'ю | implementer (той самий, продовжений) | ~596k | 73 | ~18 хв |
| Перевірка за планом | plan-verifier | ~121k | 23 | ~4.8 хв |
| Архітектурне рев'ю | architecture-reviewer | ~86k | 18 | ~2.6 хв |
| Security review (пошук) | general-purpose | ~69k | 7 | ~1 хв |
| Документація | doc-writer | ~190k | 65 | ~6.2 хв |
| **Разом агенти** | | **~1.8M** | **515** | **~73 хв** |
| Головна сесія (оркестрація, self-review, логування) | main | ~270k контексту | — | — |

### Куди пішли токени

1. **Implementer — ~58% усіх витрат** (1.04M з 1.8M). Раунд виправлень коштував більше за саму реалізацію:
   агент продовжувався з повним контекстом першого раунду, і кожен його крок перечитував цей контекст.
2. **Одні й ті самі перевірки ~5 разів** на майже однаковому коді: implementer (×2), plan-verifier,
   `/pr-self-review`, головна сесія. Кожен прогін — 10 команд (lint / typecheck / arch:check / тести × 3 пакети + sync).
3. **Повторне читання тих самих файлів.** `run-executor.ts`, контракти `vendor/shared`, `intent/service.ts`,
   `pull.repo.ts` окремо читали щонайменше 5 агентів.
4. **Довгі артефакти між агентами.** Звіт researcher (~6k токенів) повністю вставлено в промпт planner;
   план (~8k) — у промпти implementer, plan-verifier, doc-writer; звіти рев'юерів із переліком «що чисто» — 3–5k кожен.
5. **Механічні етапи на найсильнішій моделі.** plan-verifier (звірка + перезапуск команд) і doc-writer
   (переписування відомих фактів) не потребують глибокого судження.

## 2. План оптимізації (без втрати перевірок)

Принцип: зменшуємо **повтори та обсяг передачі**, а не кількість гейтів. Кожна перевірка з процесу лишається.

### 2.1 Коротші артефакти між агентами

| Що | Зараз | Пропозиція |
|---|---|---|
| План → агенти | весь текст у промпті | лише шлях `docs/plans/<feature>.md` + номери кроків (`S5–S7`); агент читає свою частину |
| Звіт implementer | довільний, 5–10k | фіксований формат ≤2k: таблиця «крок → статус», відхилення, результати перевірок; подробиці — у файлі |
| Звіти рев'юерів | знахідки + «що перевірено й чисто» | лише JSON-знахідки у форматі pr-self-review; перелік «чисто» — у файл, не в повідомлення |
| Звіт researcher → planner | повністю в промпті | researcher пише `docs/plans/<feature>.context.md`, planner читає файл |

Де змінити: секції «Output» у `.claude/agents/{implementer,planner,researcher,plan-verifier,architecture-reviewer}.md`.

### 2.2 Дешевші моделі для механічних етапів

Поле `model:` у frontmatter `.claude/agents/*.md`:

| Агент | Модель | Обґрунтування |
|---|---|---|
| plan-verifier | sonnet | звірка коду з планом, перезапуск команд |
| doc-writer | sonnet | перенесення вже встановлених фактів у документацію |
| researcher (лише репо) | sonnet / haiku | пошук і цитування `file:line` |
| перший прохід security review | sonnet | знахідки однаково проходять окремий фільтр хибних спрацювань |
| researcher (веб), planner, architecture-reviewer | сильна модель | потрібне справжнє судження |
| implementer | сильна модель для коду з безпекою / архітектурою; sonnet для механічних правок | за змістом кроку |

### 2.3 Кешування спільного контексту

1. **Context pack.** Researcher записує факти (`file:line`, що вже існує, обмеження, INSIGHTS) у
   `docs/plans/<feature>.context.md`. Наступні агенти читають його замість повторного пошуку.
2. **Кеш результатів перевірок за відбитком дерева.** Скрипт (напр. `scripts/checks-cached.sh`) рахує
   `gate.sh fingerprint`, і якщо в `.claude/pr-self-review/checks-<fingerprint>.json` уже є результат —
   повертає його, інакше проганяє перевірки й записує. Прибирає 3–4 з ~5 прогонів на фічу.
   Зміна лише `*.md` не повинна інвалідувати результати пакетних перевірок (окремий відбиток для коду).
3. **Продовжувати агента замість нового** (`SendMessage`), коли потрібен його контекст — але
   **новий агент із коротким брифом**, коли старий контекст великий, а правки локальні
   (раунд 8 виправлень коштував 596k саме через довгий успадкований контекст).
4. **Стабільний префікс промптів агентів** (правила, скіли) — щоб спрацьовував prompt cache провайдера.

### 2.4 Не надсилати diff повторно

- Рев'юер отримує `base SHA`, список файлів і **свою зону**, а фрагменти читає сам через `git diff -- <path>`:
  архітектура — `server/src/modules`, `platform`, `reviewer-core/src`; безпека — routes, adapters, git, config.
- Повторне рев'ю після виправлень — лише інкремент: `git diff <snapshot-попереднього-рев'ю>`, не вся фіча.
- plan-verifier перевіряє лише рядки матриці, які змінилися з попереднього прогону.

### 2.5 Менше агентів там, де робота послідовна

| Зараз | Пропозиція |
|---|---|
| researcher → planner | один planner, якщо зовнішні джерела не потрібні; researcher лише для вебу |
| plan-verifier + architecture-reviewer окремо | один прохід зі спільним списком файлів, або verifier лише для ризикових кроків |
| implementer для дрібних правок | дрібні локальні правки (≤ ~5 файлів, без нової архітектури) — у головній сесії |
| фільтр хибних спрацювань security | лише коли є знахідки (вже так) |

Приклад: раунд «4 зауваження + логування промпта» виконано в головній сесії, без implementer —
кілька десятків тисяч токенів замість сотень.

## 3. Очікуваний ефект

| Захід | Оцінка економії |
|---|---|
| Кеш перевірок | −10–15% (прибирає 3–4 повторні прогони) |
| Звіти ≤2k + обмін через файли | −10–20% |
| sonnet для verifier / doc-writer / security-проходу | −15–20% вартості |
| Новий агент з коротким брифом для виправлень | до −30% на раунд виправлень |
| Об'єднання researcher+planner, verifier+architecture | −10% |
| **Разом** | **≈ у 2–3 рази менше токенів на фічу такого розміру** |

Оцінки — орієнтовні, на основі одного сеансу; перевірити на наступній фічі, порівнявши з таблицею розділу 1.

## 4. Наступні кроки (потребують погодження)

1. Додати `model:` і ліміти звітів у `.claude/agents/*.md` (і оновити `.claude/agents/README.md`).
2. Написати `scripts/checks-cached.sh` і використовувати його в implementer, plan-verifier та `/pr-self-review`.
3. Додати крок «context pack» у researcher і посилання на нього в planner.
4. Після наступної фічі — заповнити таку саму таблицю витрат і порівняти.

## 5. Другий вимір — Smart Diff (2026-09-24)

Пункт 4 із розділу «Наступні кроки» виконано: нижче — та сама таблиця витрат на
фічі [Smart Diff](smart-diff.md), гілка `H03`, той самий репозиторій. На відміну
від Intent Layer, план тут **уже був готовий і погоджений** (`docs/plans/smart-diff.md`
прийшов від користувача), тому researcher і planner у цьому сеансі не викликались —
порівняння нижче враховує це.

### 5.1 Звіт по витратах

| Етап | Агент / де | Токени | Викликів інструментів | Тривалість |
|---|---|---|---|---|
| Реалізація S0–S12 | implementer | ~416k | 244 | ~27.2 хв |
| Перевірка за планом | plan-verifier | ~100k | 28 | ~3.7 хв |
| Архітектурне рев'ю | architecture-reviewer | ~61k | 14 | ~2.1 хв |
| Security review, фаза 1 (пошук) | general-purpose (fork) | ~160k | 46 | ~3.4 хв |
| Документація | doc-writer | ~137k | 57 | ~5.6 хв |
| `/pr-self-review`, спроба 1 — **порожній виклик** | fork | ~145k | **0** | ~0.04 хв |
| `/pr-self-review`, спроба 2 — фактичне виконання | той самий fork, продовжений | ~180k | 33 | ~5.1 хв |
| **Разом агенти** | | **~1.20M** | **422** | **~47 хв (агентний час; фонові прогони йшли паралельно)** |
| 2 часткові прогалини (plan-verifier) + 4 SUGGESTION (architecture-reviewer) + реальний sticky-header регрес | **головна сесія, без нового implementer** | не виміряно окремо; на порядок менше за 596k (див. §5.2) | — | — |

Для порівняння — Intent Layer (§1): ~1.8M токенів, 515 викликів, ~73 хв, разом з
researcher (~108k) + planner (~179k) і раундом із 8 виправлень (~596k, той самий
implementer, продовжений з великим контекстом).

### 5.2 Що підтвердилось

- **«Дрібні правки — в головній сесії, не новий implementer» (§2.5) працює й економить саме стільки, скільки очікувалось.**
  У Intent Layer раунд виправлень коштував ~596k токенів, бо implementer продовжувався
  з усім контекстом першого раунду. У Smart Diff три хвилі правок — 2 прогалини від
  plan-verifier (D10, S9), 4 SUGGESTION від pr-self-review/architecture-reviewer, і
  знайдений вручну sticky-header регрес — усі виправлені прямо в головній сесії
  (Edit + перезапуск лише зачеплених `lint`/`typecheck`/`test`), без жодного нового
  виклику `implementer`. Це найбільший підтверджений фактор економії цього сеансу.
- **Security review: фаза 2 лише коли є знахідки (§2.5) — підтверджено.** Фаза 1 нічого
  не знайшла → фазу 2 (паралельна фільтрація хибних спрацювань) не запускали взагалі.
  Нуль додаткових токенів на порожній результат.
- **Коротший план у промпті агента (§2.1) вже природно виконується, коли план готовий заздалегідь** —
  жоден агент цього сеансу не отримував весь текст `docs/plans/smart-diff.md` у промпті;
  кожному передавався шлях до файлу й перелік своїх кроків/файлів.

### 5.3 Нові спостереження (яких не було в §1–4)

1. **Порожній виклик форка — новий клас втрат, не тільки повторні перевірки.**
   Перша спроба `/pr-self-review` через `Agent(subagent_type: "fork")` повернулась за
   ~2 секунди з **0 викликів інструментів** і текстом "Running... in the background now" —
   форк не існує окремим фоновим процесом, він або виконує роботу синхронно в
   тому ж виклику, або не виконує її взагалі. Це коштувало ~145k токенів
   (успадкований контекст форка) за нульовий результат — довелось надіслати
   `SendMessage` з прямою вимогою виконати кроки зараз, і лише друга спроба (~180k
   токенів, 33 виклики) дала звіт. **Мітигація:** завжди звіряти `tool_uses` у
   task-notification форка з очікуваним обсягом роботи; `tool_uses: 0` на нетривіальному
   завданні — сигнал резюмнути форк з прямою вказівкою діяти негайно, а не приймати
   відповідь як завершену роботу. Варто додати цей пункт до §2 як окрему підсекцію
   («2.6 Надійність запуску форків»), бо це ризик виконання, а не оптимізація обсягу.
2. **§2.2 для `plan-verifier` досі не впроваджено.** Пропозиція від 2026-09-23 явно
   рекомендує `plan-verifier: sonnet` («звірка коду з планом, перезапуск команд» —
   механічна робота). У `.claude/agents/plan-verifier.md` станом на цей сеанс усе ще
   `model: opus` — і саме на ньому пройшли ці ~100k токенів. `architecture-reviewer`
   (`model: opus`) і `planner` (`model: opus`), навпаки, відповідають власній таблиці
   пропозиції («потрібне справжнє судження» → сильна модель) і їх чіпати не варто.
   `doc-writer`/`implementer`/`researcher`/`test-writer` уже на `sonnet`, як і
   пропонувалось. Тобто з §2.2 виконано все, крім одного рядка — `plan-verifier`.
3. **Жоден автоматичний прогін не спіймав реальний UI-регрес; ручна перевірка в
   браузері спіймала його одразу.** `plan-verifier`, `architecture-reviewer` і
   security review — усі статичні, і всі явно позначили «manual verification not
   performed» у своїх звітах. Регрес (`RoleGroup`'s sticky-заголовок рахував
   `top: 0px` через `useRef` + `useEffect` з порожніми залежностями, який
   спрацьовував до монтування виміряного елемента) — це помилка порядку рендерів,
   яку статичний аналіз коду в принципі не побачить: потрібен реальний цикл
   рендер → скрол → `getComputedStyle`. Ручна перевірка через `claude-in-chrome`
   (кілька скріншотів + `javascript_tool`) коштувала на порядок менше, ніж ще один
   раунд рев'ю, і знайшла те, що жоден з них не міг. **Пропозиція:** для кроків
   плану, що явно чіпають DOM-вимірювання/sticky/portal/timing-залежний рендер
   (не для кожної UI-фічі підряд), додати обов'язковий пункт «відкрити в браузері,
   проскролити, перевірити computed style» — до `doc-writer`, а не після нього,
   бо дешевше зловити регрес до написання документації про нього.

### 5.4 Оцінка ефекту (порівняно з §3)

| Захід | §3 оцінка | Що показав цей сеанс |
|---|---|---|
| Новий агент з коротким брифом для виправлень | до −30% на раунд виправлень | **перевершено**: 0 нових агентів на 3 хвилі правок замість ~596k токенів на implementer-раунд |
| sonnet для verifier / doc-writer / security-проходу | −15–20% вартості | doc-writer і security вже на sonnet; **verifier — ще ні** (див. §5.3.2) |
| Звіти ≤2k + обмін через файли | −10–20% | не вимірювалось окремо цього разу — потрібен інструмент підрахунку токенів по звіту, а не по всьому виклику агента |
| Кеш перевірок за відбитком | −10–15% | `scripts/checks-cached.sh` (крок 2 з §4) ще не написаний — сесія так само прогнала повний набір перевірок 3 рази (implementer, plan-verifier, pr-self-review) |

Разом: ~1.20M на фічу такого ж масштабу (63 файли, +2502/-163) проти ~1.8M на Intent
Layer, і без витрат на researcher+planner (план уже був готовий). Найбільший
підтверджений важіль — не переносити дрібні правки на новий раунд агента; найбільша
ще не використана можливість — виконати рядок 1 з §2.2 (`plan-verifier` → sonnet)
і крок 2 з §4 (кеш перевірок за відбитком).
