## Codebase Patterns

**2026-09-16** — `reviewer-core/src/review/run.ts`'s `reviewPullRequest()` already sums per-call `costUsd` into `ReviewOutcome.costUsd` (LLM pricing math lives in `server/src/platform/price-book.ts` + `server/src/adapters/llm/pricing.ts` / `reviewer-core/src/llm/openrouter.ts`) — wiring a new cost field through to `agent_runs` is pure plumbing (destructure + persist), no new pricing logic needed. Evidence: `reviewer-core/src/review/run.ts:110,159-184,216`, `server/src/modules/reviews/run-executor.ts:213`.

**2026-09-16** — `server/src/modules/pulls/routes.ts`'s per-PR list `score` is computed from the single *latest* `reviews` row per PR (by `createdAt`, the `latestReviewByPr` map) — that pattern does NOT generalize to every per-PR list field. Evidence: `server/src/modules/pulls/routes.ts:114-130`.

**2026-09-16** — Correction to the entry above: `cost_usd` on the PR list is deliberately NOT "latest review only" like `score` — it's a lifetime sum of `cost_usd` across every `status='done'` `agent_runs` row for the PR (`costByPr` map), computed independently of `latestReviewByPr`. A PR with no done runs, or whose done runs never captured cost, stays `null` (never `0`) — only add a run's cost to the sum when `costUsd != null`, and track that separately (`hasCost`) from the numeric sum so an all-null PR doesn't render as "$0.00". Evidence: `server/src/modules/pulls/routes.ts:132-150`.

**2026-09-16** — `PrMeta.findings_summary` (the list's per-severity counters) follows `score`'s "latest review only" pattern, not `cost_usd`'s lifetime-sum pattern: it reuses the same `latestReviewByPr` map (extended with the review `id`) and one batched `findings WHERE review_id IN (latestReviewIds) AND dismissed_at IS NULL`-equivalent query, then groups in JS via `summarizeFindings()`. `counts` and `items` are guaranteed to agree (not just plausibly equal) because both are derived from the exact same filtered array (`kept`) inside one function — pinned by a test that loops all three severities and asserts `counts[sev] === items.filter(...).length`. The whole path (DB read → JS filter/sort) is one query + pure grouping, with zero LLM or other network calls. Evidence: `server/src/modules/reviews/helpers.ts:95-122` (`summarizeFindings`), `server/src/modules/pulls/routes.ts:133-151`, `server/test/reviews-helpers.test.ts:90-98` (invariant test).

**2026-09-16** — Correction to the entry above: "latest review only" for `findings_summary` was a real product gap, caught live against a real (non-seed) DB — a "review all" click creates one `agent_runs` row per agent back-to-back (near-identical `ranAt`), but each agent's OWN `reviews` row is written later, whenever ITS LLM call finishes (seconds apart, LLM-latency-dependent) — so "pick the review with the newest `created_at`" silently dropped an earlier-finishing agent's findings from the very same click (e.g. Security Reviewer's WARNING vanished from the list once General Reviewer finished a moment later with 0 findings). Fixed by clustering `agent_runs.ranAt` into a "round" (`latestRoundRunIds()`, `ROUND_WINDOW_MS = 10_000`ms — generous vs. the sub-second gap between back-to-back inserts, but far short of any realistic gap between two separate clicks) and summing findings from every `kind='review'` review whose `run_id` falls in the PR's latest round, not just one. **`score` was deliberately left untouched** (still single-latest-review) since it's a separate, pre-existing field outside this feature's scope — so `score` and `findings_summary` can now visibly disagree on which agent(s) they reflect from the same round. A PR with zero `agent_runs` (only a hand-seeded review) still falls back to the single latest review. Evidence: `server/src/modules/reviews/helpers.ts` (`latestRoundRunIds`, `ROUND_WINDOW_MS`), `server/src/modules/pulls/routes.ts` (findings_summary block), `server/test/reviews-helpers.test.ts` ("latestRoundRunIds" suite), `server/test/reviews.it.test.ts` ("SUMS every agent from the latest round" / "excludes an OLDER, separate round" tests, using a direct-DB-seed `seedRoundReview()` helper since `MockLLMProvider` can't return different fixtures per agent within one app instance).

**2026-09-18** — `run_traces.trace` is plain `jsonb` with no DB-level schema — adding a new field to the `RunTrace` Zod contract (e.g. L02's `config.skills: string[]`, recording which skill ids a run's prompt actually used) needs zero migration, just a contract edit in both `vendor/shared` copies. The only place shape actually matters is `buildRunTrace()`/`RunTraceSchema.parse()` at write time and every literal `RunTrace`-shaped object in the codebase (including `run-executor.ts`'s failure-path `traceFromBuffer()`) — same "every literal builder must be updated in lockstep" trap as the `RunStats`/`RunSummary` entry above, but for `trace.config` this time. Evidence: `server/src/vendor/shared/contracts/trace.ts:74-81` (`config.skills`), `server/src/modules/reviews/run-executor.ts:266-284` (populated) vs. `:421-445` (`traceFromBuffer`, left `undefined` — acceptable since `skills` is `.nullish()`).

## Gotchas & Recurring Errors

**2026-09-16** — `RunStats`/`RunSummary` in `vendor/shared/contracts/trace.ts` type their numeric run fields `z.number().nullable()`, not `.nullish()` — the key is required even when the value is `null`. Every literal builder of a `RunStats`/`RunSummary`-shaped object (including `run-executor.ts`'s failure-path `traceFromBuffer()`, and any test fixture) must be updated in lockstep when a new stat field is added, or it fails to typecheck. Evidence: `server/src/modules/reviews/run-executor.ts:428` (`traceFromBuffer`), `server/test/contracts.test.ts:160`.

**2026-09-18** — Adding a `skills_ws_name_uq` unique index (`skills.workspace_id, skills.name`) breaks the `agents-versions.it.test.ts`-style pattern of reusing ONE literal payload constant across every `it()` in a file, when that file shares one `beforeAll`-started Postgres fixture across all its tests (as every `.it.test.ts` here does) — the second test's `POST /skills` with the same `name` 409s, so `.json().id` silently becomes `undefined` and every assertion after it fails with an unrelated-looking error ("expected undefined to be 1"), not a 409. `agents` has no such constraint so `agents-versions.it.test.ts` gets away with a shared `createBody`; any `skills`-table integration test needs a per-test unique name (a `let seq = 0` counter, e.g. `skills-crud.it.test.ts`'s `createBody()` factory). Evidence: `server/src/db/schema/skills.ts` (`skills_ws_name_uq`), `server/test/skills-crud.it.test.ts` (`skillSeq` counter).

**2026-09-18** — The three original seeded agents (General/Security/Performance Reviewer, `seed.ts`) are inserted via a raw `db.insert(t.agents)`, not `AgentsRepository.insert()`, so despite `agents.version` reading `1` in the row, they have ZERO `agent_versions` snapshots — `snapshotVersion()` only ever runs from inside the repository's own `insert`/`update`/skill-link methods. Any later write that bumps one of these agents' versions (e.g. linking a skill, which now calls `bumpVersionForSkillChange`) jumps straight from "no v1 on record" to a v2 snapshot, leaving a permanent gap at v1. Added `AgentsRepository.ensureInitialVersionSnapshot()` to backfill a missing v1 from the CURRENT row before such a write — called from `seed.ts` for General Reviewer and Security Reviewer (the two pre-existing agents L02 links skills to) but deliberately NOT for Performance Reviewer, which stays untouched (0 `agent_versions` rows) since nothing writes to it. Evidence: `server/src/modules/agents/repository.ts` (`ensureInitialVersionSnapshot`), `server/src/db/seed.ts` (`preExisting` loop).

**2026-09-18** — `fflate`'s `unzipSync(bytes)` with no `filter` option decompresses EVERY entry in the archive unconditionally, regardless of its declared size — it does not enforce any output-size bound by default. A zip whose entries are highly compressible (e.g. one repeated byte) compresses to a tiny file while declaring a huge `originalSize` in its local header — the standard zip-bomb shape (CWE-409) — and `unzipSync` will happily try to allocate and inflate all of it before your own code gets to inspect a single decompressed byte. Caught by `/pr-self-review`'s security lane on `modules/skills/helpers.ts#parseZipSkill` (an import endpoint that accepts an attacker-controlled `.zip` with no auth). Fix pattern: call `unzipSync(bytes, { filter: () => false })` first — the filter callback still fires with each entry's `{ name, size, originalSize }` from the central directory, so this pass costs nothing to decompress and gives you the full listing — decide what to keep from THAT metadata, then call `unzipSync` again with `filter: (f) => f.name === <the one entry you actually want>` to inflate only it. Evidence: `server/src/modules/skills/helpers.ts` (`parseZipSkill`), `server/test/skill-import.test.ts` ("rejects a zip bomb…", "never decompresses a skipped entry…"), `.claude/pr-self-review/H02.md` (resolved findings).

**2026-09-18** — `drizzle-kit generate` prompts interactively ("Is X column created or renamed from another column?") whenever one schema-file diff both ADDS new columns/tables AND REMOVES an existing column in the same call — it can't tell a rename from a coincidental add+drop, so it always asks, and that prompt is a raw-keypress TUI menu that does not respond to piped stdin (`printf '\n' | drizzle-kit generate` hangs/no-ops, it does not accept the default). Worked around by splitting one logical schema change into two `generate` calls: first commit the schema edit with the new columns/table added but the old column still present (a pure-ADD diff — no prompt), run `generate`, THEN remove the old column and run `generate` again (a pure-DROP diff — also no prompt). Produces two small auto-named migrations instead of one combined one, which is fine (both are still `drizzle-kit`-generated, never hand-named). Evidence: `server/src/db/migrations/0013_clear_manta.sql` (adds `conventions.category`/`.../status` etc. + the whole `convention_scans` table, `conventions.accepted` still present), `server/src/db/migrations/0014_legal_chronomancer.sql` (`ALTER TABLE conventions DROP COLUMN accepted` — nothing else in the diff, so no prompt).

**2026-09-20** — A skill file under `.claude/skills/<name>/SKILL.md` and a row in the `skills` table are two unrelated systems that happen to share the word "skill": the former is a Claude Code / `/pr-self-review` instruction loaded by the coding agent in the terminal, the latter is the only thing `ReviewRunExecutor.buildSkillBlocks()` can put into an in-app agent's prompt (via `agent_skills` → `SkillsRepository.forAgent()`). Adding `.claude/skills/breaking-change` etc. therefore changes nothing about what the seeded API Contract Reviewer sends to the model, and the skill never appears in that agent's run log — a reviewer on PR H02 read the repo the other way round. Shipping a review rule to BOTH places means: a prompt-sized body in `server/src/db/seed-skills.ts`, an entry in `seedSkills` + the agent's `skills: [...]` array in `seed.ts`, a mirror under `docs/agent-prompts/skills/`, and (for the Claude Code side) `.claude/skills/pr-self-review/routing.md`. Evidence: `server/src/modules/reviews/run-executor.ts` (`buildSkillBlocks`), `server/src/db/seed.ts` (`seedSkills`, `seedSkillAgents`), `docs/agent-prompts/skills/README.md`.

**2026-09-23** — `modules/settings/feature-models.ts`'s `resolveFeatureModel`/`getFeatureModelOverride` used to take the full `Container` type just to reach `container.db`. Calling `resolveFeatureModel` from inside `platform/container.ts` itself (the composition-root-only pattern the Intent Layer plan required, vs. the older convention of calling it straight from a module's `routes.ts`) makes `container.ts` import `feature-models.ts`, which already imports `Container` from `container.ts` — a real `no-circular` failure under `pnpm arch:check` (`src/modules/settings/feature-models.ts → src/platform/container.ts → src/modules/settings/feature-models.ts`), not just a style nit. Fixed by narrowing both functions' parameter type from `Container` to a local `HasDb { db: Db }` interface — `Container` still satisfies it structurally, so every existing call site (`resolveFeatureModel(c, …)` from a module's `routes.ts`) keeps compiling unchanged. Evidence: `server/src/modules/settings/feature-models.ts` (`HasDb`), `server/src/platform/container.ts` (`intentService()`).

**2026-09-23** — A service that keeps per-instance in-memory state (e.g. `IntentService`'s single-flight `Map`) is silently useless if the container method that builds it isn't memoized: `modules/intent/routes.ts` and `reviewService()` (→ `ReviewRunExecutor`) each call `container.intentService()` once, at their own plugin's registration — an unmemoized factory method (`intentService(): IntentService { return new IntentService(...) }`) hands each caller a DIFFERENT instance with its OWN empty map, so two calls for the same PR routed through different callers (a manual `POST` vs. a background review-triggered derive) never see each other's in-flight promise and both hit the model. The fix is the same `this._x ??= new X(...)` memoization every other container-provided repository already uses (`agentsRepo`, `reviewRepo`, …) — but it's easy to miss specifically for a *service* (as opposed to a repository) because nothing about "wire it from ports" signals "and cache the instance too". Evidence: `server/src/platform/container.ts` (`intentService()`, `_intentService`).

**2026-09-24** — `pnpm arch:check`'s `no-sideways-module-imports` rule (`.dependency-cruiser.cjs`) flags a cross-module `import type { ... } from '../other-module/repository.js'` exactly the same as a value import — dependency-cruiser tracks TypeScript type-only edges as real dependencies by default, so marking the import `import type` does NOT exempt it. A new module whose port structurally satisfies an existing module's repository (D2-style, e.g. `smart-diff`'s `SmartDiffStore` vs. `pulls`'s `PullsRepository`) must declare its OWN minimal structural types for whatever it needs (a `{ id: string }` stand-in for `Pull`, a local `SmartDiffFindingInput` instead of importing `FindingsInput`) rather than importing the other module's `repository.ts` types at all — even read-only, even type-level. Importing types from a sibling module's `helpers.ts`/`constants.ts` (not `service|routes|repository`) is fine per the same rule's `to.path` regex. Evidence: `server/.dependency-cruiser.cjs:82-92` (`no-sideways-module-imports`), `server/src/modules/smart-diff/service.ts` (`SmartDiffStore`), `server/src/modules/smart-diff/helpers.ts` (`SmartDiffFindingInput`).

**2026-09-24** — `SmartDiff.split_suggestion` (`too_big`/`proposed_splits`) is a real, always-present field on the wire, but `buildSmartDiff` only ever emits `SPLIT_SUGGESTION_DEFAULT` (`too_big: false`, `proposed_splits: []`) plus a computed `total_lines` — no code path in this module sets `too_big: true` or proposes an actual split. Don't assume the field being populated on every response means the "this PR is large, consider splitting" feature is implemented; only the byte count is real today. Evidence: `server/src/modules/smart-diff/constants.ts:18` (`SPLIT_SUGGESTION_DEFAULT`), `server/src/modules/smart-diff/helpers.ts:74` (only `total_lines` is computed).

## Open Questions

Right now a REAL, still-unfixed CRITICAL from an older review silently disappears from every counter the moment a newer round supersedes it — even if that newer round found nothing only because of an unrelated environment problem, not because the issue was fixed. Observed live on acme/payments-api PR #482: a 2026-09-14 seeded review flagged a hardcoded Stripe secret key (CRITICAL), but the PR list now reads "Findings: 0" because three 2026-09-16 real agent runs (one round, per `latestRoundRunIds`) found nothing — not because the secret was removed, but because `clone_path` was null so the diff was empty and the code was never actually re-examined.
